Phase 1

Fix what is actually broken

Each of these produces a wrong or fatal result in the current build. They rank above every new capability below, because shipping more features on top of a broken default path compounds rather than adds.

specs/048open finding

The guided-init auto-launch kills the whole stack

Effect
orchestrai init → Ctrl+S in a real terminal — the default interactive path — starts all six services, reports every one healthy, then dies about a second later while creating a second CliRenderer. Already isolated to an application-free repro containing none of this repo's code.
Value
A shipped feature is broken in its own default mode. Anyone using init from a real terminal hits this; only --headless escapes it.
Cost
Small code change, real decision: work around it by spawning the viewer as its own process, or wait on upstream @opentui/core. Closes 048 rather than opening a new spec.
specs/058drafted

Testing Agent calls every Node project “bun”

Effect
detectRunner() classifies any package.json with a test script as Bun. A real Jest or Vitest project gets bun test in the approval preview a human is asked to sign off on.
Value
Not a crash — a plausible-looking wrong answer, which is the worse failure. Replaces the guess with real lockfile/manifest detection, and reports ambiguity instead of picking one.
Cost
Medium. Real fixture projects per ecosystem, plus one RUNNER_ARGV entry per newly supported profile. Go / Rust / .NET deliberately deferred.
specs/056drafted

Existing files can still be silently overwritten

Effect
Adds create / no-op / update / blocked classification before any DevOps write. An exact no-op never reaches a write tool at all, and the approval binds a content fingerprint re-checked immediately before the real write.
Value
Closes the post-approval drift window — a file changed after you approved can no longer be written over unreviewed. Applies to all four write skills, not just Dockerfiles.
Cost
Medium. Touches the four write paths and the ApprovalPreview shape; no change to the approval gate's own mechanics.
Phase 2

Real capability leverage

Nothing here is broken today — these make the system meaningfully more capable, and both are small because they reuse machinery that already exists.

specs/060proposed

Parallel dispatch, read-only steps first

Effect
The supervisor may fan out several read-only steps concurrently instead of one at a time. A plan opening with analyze-project plus git-status stops being sequential for no reason.
Value
Real wall-clock speedup on multi-step plans, and it sidesteps the hard problem entirely: read-only skills have no approval gate, so concurrent approvals never arise. SKILL_TIER_REGISTRY already knows which skills qualify.
Cost
Small. Promise.all() inside the existing dispatch node, gated on every branch being read-only. The two runaway bounds must count per branch.
specs/054drafted

Capability-driven routing tier

Effect
Adds an LLM router below keyword matching and the local classifier, consulted only when both miss, validated against the live Agent-Card capability snapshot before anything dispatches.
Value
Unusually-phrased requests reach the one skill they actually meant, instead of falling through to a full plan-task run. The approval gate is untouched — a router-named write still needs the same human click.
Cost
Small. One structured completion plus a schema, following the Security harness shape — no graph, because there is nothing for a loop to loop on.

specs/057drafted

Project snapshot reuse within a conversation

Effect
Read-only inspection results are cached per conversation, fingerprinted and TTL-bounded. Writes always re-check fresh regardless of cache age.
Value
Stops re-inspecting the same project on every follow-up turn in a thread. Asking about status then asking to dockerize no longer pays for the same inspection twice.
Cost
Medium, and best sequenced after 056 so one fingerprint definition stays authoritative instead of two independently invented ones.
specs/059spike first

Paste actually works in the TUI

Effect
Bracketed paste into chat, the task composer, target paths, model names, and the masked key field — as one atomic insertion, size-bounded, never interpreted as keybindings.
Value
Removes a real daily friction: pasting a project path or an API key is the most obvious thing to do and currently the thing that does not work.

Unknown until a spike. The mechanism exists in @opentui/core, but whether this repo's deliberately hand-rolled fields can receive it is unverified. Approval buys the research, not a guaranteed fix.

Phase 4

Parked — start only on a trigger

Each of these is real work with a real payoff, and none of it is worth starting now. The trigger matters more than the item: begin when the named condition actually occurs, not because the list has an empty slot.

specs/055deprioritized

Provider budgets and transient-error retry

Effect
Distinguishes a transient 429 or 5xx from a permanently bad key, and retries only the transient one with bounded backoff. Today both fail a task closed, identically.
Value
A rate limit resolves itself in under a minute; killing the whole task for it is wrong. Matters more since 051 removed the deterministic fallback.
Cost
Trigger: a rate limit or provider outage bites again, or someone else runs this on a free tier. You deprioritized it deliberately after moving off free.

Deliberately not on this plan

Naming what is excluded is half the value of a roadmap — each of these was considered in this session and rejected for a specific reason, not overlooked.

  • Full AG-UI adoption / @ag-ui/langgraph. Requires a deployed LangGraph API server plus its own databases. Your spike already found no embedded-execution mode, and it would break the single-binary distribution you shipped today.
  • LangGraph Server / Platform. Real persistence and native resume, but it means a new always-on service, Postgres and Redis, and re-deriving every one of spec 028's safety guarantees against a different execution model.
  • Level-3 parallel dispatch with concurrent approvals. Two simultaneous write-capable steps break "rejection is terminal" and require both clients to render N pending approvals. Revisit only if Phase 2's read-only fan-out proves insufficient.
  • Wrapping single-shot LLM calls in graphs. A one-node graph is state schema, edges and a recursion limit that never decide anything — the same bug surface as spec 028's real event-correlation bug, for no payoff.
  • A CI-provided provider key. Spec 052 already proves dispatch works with a deliberately fake key; spending real quota on every pull request buys nothing.
Sequencing rationale: broken before missing, missing before slow, slow before speculative. Every item above needs its own approval before implementation, per CLAUDE.md working-procedure step 8 — this plan orders the queue, it does not authorize any of it.
