Every write-capable action — the four DevOps skills and any test run — stops and shows a preview with the exact content that will be written, a diff against what's already there when overwriting, and waits for a person. That gate is the one property that has not changed shape across all 64 checkpoints below.

How it's built

Six processes, two protocols, one adaptive planner

A2A-style HTTP moves tasks between the Orchestrator and its four agents; MCP exposes tools (git, file, analysis) to the three agents that need them. Security stays direct-filesystem by deliberate decision — already read-only and audited, converting it would cost real performance for architectural symmetry alone.

The adaptive planner, specifically

When a request is broad ("build and deploy my app") rather than a direct skill, the Orchestrator's own supervisor decides one step at a time — dispatch a skill, observe what actually happened, decide the next step. A failed read-only step lets it try something else; a failed write-capable step is treated as ambiguous and stops the run rather than assuming nothing happened. This replaced a separate, deleted Planning Agent — the Orchestrator itself is now the only planner, and it refuses to even start without a working provider key.

How specs work

Nothing changes behavior without a written, approved checkpoint first

Every one of the 64 checkpoints above exists as a file under specs/ before the code that implements it. This isn't a suggestion — it's a hard stop enforced in the working process itself.

The rule that actually enforces it

Before touching runtime behavior, architecture, or protocols: read the operating guide, write a numbered spec with schema-validated metadata (a stable area, a change type, safety constraints, acceptance criteria), run the catalog governance check, and present it. Then stop. No file gets edited outside specs/ until there's an explicit approval — this applies to every coding agent working in the repo, and a spec's own draft banner is never itself authorization. A pre-commit hook runs the same governance check plus the full test suite on every commit, so a spec with bad metadata or a broken build cannot land silently.

Three checkpoints are exactly that right now, all sitting at this gate, waiting on review: specs/063 (letting each agent pick its own provider, not only its own model), specs/064 (the supervisor's startup key check becomes a warning instead of a hard stop), and specs/065 (retiring keyword/local-classifier routing in favor of the LLM router deciding every skill dispatch — the biggest architectural bet in the queue, and the one most likely to change what Figure 1 above looks like if approved).

The published npx orchestrai package is 21 commits behind what's actually in this repo right now.

The honest one-line version: the architecture's core safety claim — a write always stops for a human, nothing bypasses that — is proven repeatedly and adversarially. What's unproven is provider behavior under real conditions with two of three providers, and whether any of this survives a process restart. Neither is a flaw in the design; both are work that hasn't happened yet.
