Live-demo reference · OrchestrAI

Which wire is this, again?

Three different mechanisms move data between OrchestrAI's pieces — the custom A2A-style task protocol, real MCP over Streamable HTTP, and plain internal execution with neither. This page maps every demoable action to the mechanism it actually uses, so you can narrate it correctly while it's happening on screen.

00 Color key — used across the diagrams below

A2A-style · Orchestrator ↔ Agent A2A · direct, Agent ↔ Agent (Tier 3) MCP · Streamable HTTP tool call Internal only · no network hop Local classifier · routing decision, no hop at all

01 System map

Every agent talks to the Orchestrator over the same A2A-style protocol. DevOps, Testing, and Documentation are all real MCP clients (sharing one connection-lifecycle implementation); only DevOps additionally makes one direct, Orchestrator-bypassing A2A call — to Security, during analyze-project. Planning and Security are the two agents that never leave their own process — Security by deliberate decision (already read-only/audited, converting it would cost latency for architectural symmetry alone).

02 Routing: keyword match, then a local classifier

Before any of the three wires above get chosen, the Orchestrator first has to decide which skill a task is for at all — that decision itself is not a wire hop; it all happens inside the Orchestrator's own process (detectSkill()), before the winning skill's agent is ever contacted over any protocol.

Try it live: a phrase with no matching keyword, e.g. "can you check if my repo has any leaked keys" — still correctly routes to scan-secrets, with no "secret"/"scan" keyword anywhere in the text. There's no wire-level audit line for this step the way there is for MCP/A2A below — the tell is the assigned skill itself, visible in the task response and every dashboard/TUI.
