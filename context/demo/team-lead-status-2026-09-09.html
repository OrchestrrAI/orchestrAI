Claude and GPT paths have never made a real API call

critical

Every live-provider verification recorded in this project's history — routing, retry, the planning harness, the conversational layer — was run against Gemini only. The Anthropic and OpenAI code paths are complete (same shared LangChain boundary, same tests, same typecheck) but zero real request has ever gone out on either. This is exactly the gap Yusuf flagged going into this review.

Closes with: one short session, real keys for both providers, a deliberate bad-key case (should fail immediately) and a real success case per provider. No spec needed — this is proving existing code, not building anything.

Approval state is memory-only

critical

The entire safety mechanism — a write requires a server-issued actionId bound to immutable parameters — lives in a plain in-memory Map per agent. Restart any agent mid-approval and that binding is gone; the orchestrator keeps waiting on a promise that will never resolve. This is a documented invariant with no durability behind it, not generic "add a database" debt.

Closes with: a new spec — durable task/approval state, file-backed, no new dependency (matches this repo's own minimalism precedent).

The newest retry logic is untested against a real error

needs a live pass

Spec 055's provider-error classifier (which decides "retry" vs. "fail now") was written against each provider's documented error shape, not a captured real one. If a real error nests its status differently than assumed, a genuine rate limit could silently classify as permanent — and every existing test would still pass, because they feed the shape that was assumed. I wrote this code; it hasn't met reality yet.

Closes with: the same live-provider session as the item above — this is the direct payoff of validating Claude/GPT for real.

New spec, awaiting approval — Per-agent provider selection

specs/063-init-per-component-provider-and-key — not yet approved, no code written. Per this repo's own process, nothing gets implemented until it's reviewed and signed off.

Today's setup UI (classic wizard, TUI form, browser form) lets you pick a different model per agent — a cheap model for DevOps parameter-picking, a stronger one for the orchestrator — but only one shared provider and key for everything. This spec exposes per-agent provider and key too, closing the exact footgun the prior decision worried about: a provider chosen with no matching key would silently fall back to the wrong provider's key and surface as a confusing auth error later, not at setup time. The new design makes that state impossible to produce — a provider change and its key change together, always, and an unset key is a setup-time validation error, never a runtime surprise.

  • Setting a per-agent provider with no key: rejected at setup, not silently written.
  • Leaving every agent at the shared default: writes the exact same config as today, byte for byte.
  • Clearing an override removes both its provider and key lines together — never one orphaned.
