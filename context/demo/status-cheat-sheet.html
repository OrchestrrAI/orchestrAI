01 System map — what changed

Four agents are now real MCP clients, not three: Planning joined them, but only through its harness and only for two read-only tools. Security remains deliberately direct-filesystem. The genuinely new edges since the original sheet are Planning's read-only MCP access, its optional call out to an LLM provider, and the AG-UI event stream feeding both clients.

02 How a skill gets chosen — three tiers, in order

This is the answer to "is it just calling an LLM for everything?" — no. Each tier only runs if the one above it found nothing, and the approval gate is identical regardless of which tier decided.

Most of this system is deliberately not AI. The non-deterministic part is allowed to suggest; it is never what makes something safe.

03 The approval gate — and which port enforces it

The most important thing on this page. There are two /approve endpoints and they do different jobs. Demonstrating the wrong one makes a working gate look broken.

Demo trap

Run the "forged approval" beat against :3002. Against :3000 an empty body succeeds and writes the file — correct behavior, since that hop is a trusted forwarder rather than the enforcement point, but on stage it reads exactly like a bypassed gate.

What the gate actually guarantees

The preview a human sees carries the exact tool, absolute target path, full parameters, overwrite flag and risks. The actionId is bound to those exact parameters, so nothing can change between preview and execution. It is a stale-action and correlation guard — not a secret, not proof of identity.

04 Skill dispatch is authoritative now

New since the original sheet, and worth knowing because it came from a real incident. Previously an agent re-derived the skill from the task's free text, even when the Orchestrator had already decided one.

The bug, found live

An LLM-authored plan step was correctly named git-status, but its description mentioned an observed Dockerfile. The receiving agent ran its own text detector over that description, matched dockerize, and queued a file write instead.

The approval gate caught it — the action stopped at input-required and was rejected, nothing was written. But skill identity itself had not been authoritative.

The fix

The Orchestrator now sends the skill it already decided on with every dispatch, and every agent executes exactly that — never re-deriving one from description text. Agents also validate that they actually own the skill they were handed. Legacy submissions without the field keep the old text-detection behavior unchanged.

05 The live event stream is protocol-conformant

GET /events emits AG-UI events sourced from the official @ag-ui/core package, and every event is validated against the real schemas at runtime before it reaches the stream — not merely typed against them. Two independent clients consume it.

Honest detail worth telling

Adopting the official schemas proved an earlier claim wrong: two of the nine event types did not actually conform — TOOL_CALL_RESULT was missing a required messageId, and RUN_FINISHED.outcome was a bare string where the schema requires an object. Both were fixed rather than documented as deviations. All nine now genuinely validate.

The approval CUSTOM events are informational only. AG-UI has no native human-in-the-loop primitive, so a client must never treat one as authorization — approving still requires the real actionId-bound request.

06 The LLM harness — scoped deliberately narrow

What it can do

  • Run only for Planning's plan-task skill
  • Call exactly two read-only MCP tools: git_status, analyze_project
  • Loop: decide → call → observe → decide again
  • Name skills only from a live capability snapshot of what agents actually advertise

What it structurally cannot do

  • Reach any write-capable tool — the graph builder throws at build time if edited to bind one
  • Invent a skill: output is schema-validated before dispatch
  • Run at all unless ORCHESTRAI_LLM_HARNESS=1 and a key are set
  • Weaken the approval gate in any way

Fail-closed, not fallback

Invalid output gets one bounded retry with feedback. Exhausted retries, an API error, a timeout or a tool failure all resolve to zero plan steps — the same "no actionable steps" response the keyword path gives for unmatched input. It never silently falls back to another provider or to the keyword planner.

07 Status — what's real, what isn't

Real and verified

  • MCP over Streamable HTTP, 13 tools
  • Agent-to-agent HTTP, including one Orchestrator-bypassing hop
  • Real file writes against a real target project, behind the gate
  • Live SSE to two independent clients
  • 277 tests · 0 type errors · CI green on Windows and Linux
  • One standalone binary (~140 MB) — no Bun, no source tree needed
  • 30 governed specs; every behavioral change reviewed before written

Deliberately not done

  • No persistence — all task state is in memory
  • No authentication or authorization
  • Ports and agent URLs are hardcoded
  • No production sandbox beyond path containment and a no-shell execution boundary
  • No Coder or Code Review agent
  • Parent plan status reports the dispatch loop finishing, not that every step succeeded
It's a prototype with a real safety model — not a production platform. The boundaries are the part we actually finished.
