# Verification: Ambiguous-Runner Harness Resolution and Read-Only document-api Harness Reachability

Date: 2026-09-22

## Summary

Both fixes implemented exactly as specced:

- **Fix 1 (A9)**: `packages/agents/documentation/index.ts`'s
  `skillDocumentApi()` now calls `computeApiDocOrHarness()` instead of
  `computeApiDoc()`. The dead `allowWrite: true` branch derives
  `savePath` via `extractSavePath(text)` instead of destructuring it
  from `computeApiDoc()`'s own return shape (which
  `computeApiDocOrHarness()` doesn't have — it returns a bare string).
- **Fix 2 (A2)**: `packages/agents/testing/index.ts`'s `processTask()`
  ambiguous-runner branch (`run-tests`/`check-coverage` only —
  `write-tests`'s own branch is untouched) now calls
  `handleUnsupportedRunner()` when an explicit command is already in the
  text or the harness is genuinely on, and falls back to the original
  static ambiguity report otherwise — guarding against
  `handleUnsupportedRunner()`'s own harness-off state producing the
  misleading "no tests configured" text for a project that plainly has
  tests.

## Live verification (real processes, real files, no mocks)

A scratch MCP HTTP server plus scratch Testing and Documentation agents
were started against real scratch projects, using this repository's own
real `.orchestrai/config.env` credentials (a real Gemini key).

**Fix 2 (A2) — ambiguous-runner resolution.** A real scratch project
(`package.json` with `scripts.test`, both `package-lock.json` and
`pnpm-lock.yaml` present — a genuine `detectRunner()` `{kind:
"ambiguous", candidates: ["npm", "pnpm"]}`), harness genuinely on
(`gemini-3.1-pro-preview`). `POST /` `"run tests at <path>"` reached
`input-required` with a real, model-proposed `["npm", "test"]` command
— the model genuinely resolved the npm/pnpm ambiguity from real file
reads, landing on one of the two actual candidates, not a hallucinated
or arbitrary choice. Rejected afterward (no execution needed to prove
the routing fix). This is the decisive scenario: before this fix, the
identical request with the harness on would still have produced only
the static "Ambiguous... resubmit" text, since the ambiguous branch
never called into the harness at all.

**Fix 1 (A9) — read-only document-api harness reachability.** A real
scratch PHP file (`routes.php`, three genuine Laravel-style
`Route::get`/`post`/`delete` registrations — the exact case
`scanApiRoutes()`'s fixed JS/TS regex finds zero matches for).

1. First attempt used the model already configured in the repo's real
   config (`gemini-2.5-flash-lite`) and failed with a real provider
   error: *"This model models/gemini-2.5-flash-lite is no longer
   available to new users..."* — itself decisive evidence the fix
   works: before this fix, a read-only request never reached the
   harness at all, so no model call (successful or failed) would ever
   have been attempted.
2. Restarted with an explicit working model override
   (`ORCHESTRAI_DOCUMENTATION_LLM_MODEL=gemini-3.1-pro-preview`, the
   same override mechanism `specs/039`'s per-component config already
   provides). Identical read-only request now produced real, grounded
   Markdown documentation for all three real routes (`GET /users`,
   `POST /users`, `DELETE /users/{id}`), including a real path
   parameter description — genuinely generated by the model reading the
   real file content via `specs/100`'s own route-discovery fallback,
   not a template.
3. Restarted a third time with the harness explicitly off
   (`ORCHESTRAI_DOCUMENTATION_LLM_HARNESS=0`). The identical read-only
   request against the identical file reproduced the exact pre-fix
   deterministic output: `"No Hono route registrations found
   (app.get/post/put/delete)."` — confirming the harness-off regression
   guarantee holds exactly, byte-identical.

Both scratch processes and their scratch directories were torn down
after verification; no state from this pass was left running or on
disk.

## Narrative record (relocated from CLAUDE.md, 2026-09-23, specs/118)

**Correction, 2026-09-22 — read-only `document-api` now reaches the
harness too.** `specs/111-testing-documentation-routing-fixes/spec.md`
(implemented, verified) closed a real inconsistency (`specs/104` item
A9): `skillDocumentApi()`, the function the **read-only** call site
uses, called the purely deterministic `computeApiDoc()` regardless of
harness state — only a "save to" request reached
`computeApiDocOrHarness()`. Same file, same harness state, two
different answers depending only on phrasing (a "save to" PHP request
got a real analysis via `specs/100`'s route-discovery fallback; a bare
read-only request got "No Hono route registrations found"). Fixed by
swapping that one internal call; `computeApiDocOrHarness()` already
falls back to the identical deterministic output when the harness is
off, so this is a strict superset with no regression. Live-verified: a
real scratch PHP file, harness on, produced real grounded documentation
for all three real routes read-only; the identical request with the
harness off reproduced the exact pre-fix text, byte-identical.

**Correction, 2026-09-22 — `run-tests`/`check-coverage`'s own ambiguous
branch now attempts resolution too.** `specs/111-testing-documentation-
routing-fixes/spec.md` (implemented, verified) closed `specs/104` item
A2: the `{kind: "unsupported"}` branch already routed through
`handleUnsupportedRunner()` (`specs/080`'s own 4-state harness fallback)
right next to a `{kind: "ambiguous"}` branch that just returned a
static "resubmit naming which one" report and never attempted anything,
even with the harness on. Fixed for `run-tests`/`check-coverage` only —
**`write-tests`'s own ambiguous handling is deliberately untouched**,
per `specs/081`'s own considered non-goal (guessing a framework on top
of authoring test content compounds two guesses in one step). A real
subtlety found while implementing, not assumed: naively reusing
`handleUnsupportedRunner()` unconditionally would be wrong, since its
own harness-off state says "no tests configured" — false and misleading
for an ambiguous project that plainly has tests. The fix only routes
into resolution when an explicit command is already in the text or the
harness is genuinely on; otherwise the original honest ambiguity report
is unchanged. Live-verified: a real scratch project with genuinely
conflicting npm/pnpm lockfiles, harness on, produced a real
model-proposed `["npm", "test"]` — the model resolved the ambiguity
from real file reads, reaching the identical `run-command`-style
approval gate every other harness-proposed command already uses.
